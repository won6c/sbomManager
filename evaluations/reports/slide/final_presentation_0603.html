문제 정의 / 동기 / 목표

문제: SBOM은 목록이지만, 실제 공격 표면은 관계다

사용자 스토리

보안 분석가

실행 중인 서비스, 바이너리, 패키지, 취약점을 연결해서 단순 CVE 목록이 아닌 실제 공격 가능한 표면을 우선순위화하고 싶다.

취약점 관리자

외부에 열린 포트가 어떤 프로세스와 바이너리에서 왔는지 확인하고, 패치 전후 위험 변화까지 비교하고 싶다.

프로젝트 목표

  • 수집: kernel, daemon, binary, package 상태를 probe로 자동 수집
  • 상관분석: port -> PID -> binary -> package -> CVE 관계 구성
  • 위험평가: 노출도, 완화기법, TARA feasibility를 반영
  • 운영화: API, dashboard, scan history, comparison으로 반복 분석 지원

Scrum 방식의 테스트와 평가

각 스프린트 종료 기준: 구현 완료가 아니라 검증 로그까지 남기는 것

1. Sprint Planning

  • tasks/progress.json active_todo 기준으로 scope 선택
  • tasks/todo/TODO_TRACKING.md에 완료/보류 기준 명시
  • 각 기능의 검증 명령을 먼저 정함

2. Daily Build/Test

  • 작은 단위 구현 후 pytest 실행
  • scripts/build.sh로 import/schema 오류 확인
  • FastAPI TestClient로 endpoint smoke test

3. Review & Retrospective

  • tasks/done/SESSION_LOG.md 기록
  • 남은 TODO는 completed/deferred로 재정리

팀원별 기여

  • 양병규: CPE/CVE API 담당 - CPE resolver와 CVE/NVD provider를 연결해 자산을 공개 취약점 데이터와 매핑.
  • 강민성: Package Probe 담당 - dpkg-query와 Python dist-info를 활용해 package name, version, ecosystem, PURL 수집 로직 구현.
  • 최원준: 구현 및 전체 통합 담당 - architecture, collector, kernel/daemon/binary probe, graph/risk, remediation, scan history, UI, tests, docs, integration 수행.

Challenges -> Lessons

NVD API rate limit
외부 API 의존성을 줄이기 위해 cache/offline-friendly provider가 필요함.

FastAPI JSON recursion
Pydantic 모델과 jsonable encoding을 명시적으로 관리해야 함.

TODO drift
progress.json을 active scope의 single source of truth로 유지해야 함.

CVE count 한계
실제 위험은 CVE 개수보다 exposure, reachability, mitigation으로 결정됨.
