Problem & Motivation

Problem

  • 기존 SBOM은 패키지 목록 중심이라 실제 실행 환경과의 연결이 약함
  • 커널, 데몬, 바이너리, CVE를 각각 확인해야 해 분석 누락 위험이 큼
  • 취약점 존재 여부만으로는 실제 노출 위험도를 판단하기 어려움

Motivation

  • 실행 중인 자산과 취약점 정보를 연결해 우선순위 판단 지원
  • 반복 가능한 스캔과 표준 JSON 결과 제공
  • 향후 SBOM upload, package probe, exploit intelligence 확장 기반 마련
As a security analyst, I want to map running services, binaries, kernel state, and vulnerabilities, so that I can prioritize real exploit surfaces.

Project Overview & Goals

Major Features

  • FastAPI 기반 `/health`, `/scan` API

  • 권한 제한 상황에서도 graceful degradation 제공

Challenges

  • Linux 권한 차이: `PRIVILEGE_RESTRICTED`로 graceful degradation 적용
  • 외부 API 의존성: cache, retry, fallback CPE generation 적용
  • JSON serialization: Pydantic model과 `jsonable_encoder` 사용
  • 환경별 결과 차이: mock test와 verify script 분리

Lessons Learned

  • 보안 도구는 데이터 연결 구조가 중요함
  • 문서화는 개발 중 의사결정 기록으로 관리해야 함
  • 플러그인 구조는 기능 확장과 테스트 분리에 효과적임
